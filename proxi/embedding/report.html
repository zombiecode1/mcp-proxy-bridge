Embedding + Agent Architecture Notes (proxi)

Generated: 2026-05-27. Audience: maintainers of this repo. Language: English only (codebase constraint).
Implemented OpenAI-Compatible Tool Calls SQLite State DB (local-first) RAG Quality Depends on SSOT Content Vector Store (Qdrant) Not Enabled Yet

1) Current Endpoints (Server)

OpenAI-Compatible

  • POST /v1/chat/completions - Supports tools, tool_choice, streaming, vision content parts (pass-through)
  • POST /v1/completions - Legacy text completions wrapper
  • POST /v1/audio/transcriptions, /translations
  • POST /v1/embeddings - Requires an embeddings model to be available on Groq account
  • GET /v1/models, GET /v1/models/:id

Agent / RAG

  • POST /v1/agent/chat - Default mode returns OpenAI chat.completion objects; legacy mode ({"legacy": true}) returns AgentResponse wrapper.
  • POST /v1/agent/directory - Sets working directory; permission gating applies unless the workspace is trusted.
  • POST /v1/agent/permission - Grants scan/write/execute permissions and may create .zombiecoder/SSOT.md.
  • GET /v1/agent/status, GET /v1/agent/ssot, GET /v1/agent/routes

2) Model Routing (Agent)

Routing is handled by src/services/mawlanaRouter.ts. It picks from a preference list, but always resolves against the /v1/models list actually loaded from Groq. This avoids routing to non-existent models.

Categories: chat, code, rag, guard.

3) Rate Limit Behavior

To reduce accidental "TPM requested" failures, the bridge now defaults to max_tokens=1024 if the client does not specify a completion token budget. The client can override with max_tokens.

4) SQLite State Store

A local SQLite file is created at .zombiecoder/state.db under the workspace. Tables are created for: personas, models, model rate limits, workspaces (trusted directory gating), conversations, and conversation messages. 

Tables:
  agent_personas(persona_id, name, system_prompt, updated_at)
  models(model_id, owned_by, category, context_window, max_tokens, updated_at)
  model_rate_limits(model_id, rpm, tpm, updated_at)
  workspaces(workspace_id, user_id, directory, trusted, created_at, updated_at)
  conversations(conversation_id, workspace_id, user_id, title, created_at, updated_at)
  conversation_messages(id, conversation_id, role, content, created_at)

5) Workspace Trust / Permission Flow

Default behavior is conservative: a directory requires explicit permission unless it is marked trusted for the given (user_id, workspace_id, directory) in SQLite. If trusted, the agent can auto-initialize .zombiecoder/ and create SSOT.md without asking.

Request fields supported: 

{
  "directory": "/abs/path/to/project",
  "user_id": "admin",
  "workspace_id": "local-workspace-1"
}

6) RAG Reality Check

The current SSOT is a structural inventory (tree + file list). This is useful for discovery, but it is not enough for high-quality "answer from code" behavior. For better RAG, SSOT should include summaries of key modules, routes, and configs, and/or a separate index should store chunked file contents.

7) Embeddings and Vector Store Plan

This repo includes local embedding model artifacts under ./embedding/. The recommended practical approach is:

  • Use an in-process embeddings library (e.g. FastEmbed) to generate vectors for chunks.
  • Store vectors in Qdrant (runtime) under a per-workspace collection name.
  • Keep only small, relevant runtime state in the vector DB; keep authoritative state in SSOT + SQLite.

8) Groq Tool Use: Built-In Tools vs Remote MCP vs Local Tool Calling

Groq documents three tool use patterns:

  • Built-in tools: zero orchestration (Groq executes tools server-side).
  • Remote MCP: connect the model to an MCP server URL (HTTP/SSE or stdio), and Groq performs tool discovery and calls.
  • Local tool calling: you implement tool execution on your side; the model outputs tool calls.

Recommendation for this project:

  • If you need strict local-first behavior and full auditability, prefer local tool calling + SQLite logs.
  • If you want minimal glue code for external SaaS integrations, remote MCP can be reasonable, but you must treat MCP server uptime and rate limits as a production dependency.
